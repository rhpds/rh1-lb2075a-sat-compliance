# Module 09 — Run an OpenSCAP scan on a host

## Brief Overview

This capstone module ties together everything built in the previous eight modules. Participants trigger OpenSCAP compliance scans on both RHEL hosts from the Satellite Web UI, monitor the Remote Execution jobs to completion, and then navigate the compliance report to identify the discovered violation — SSH access with empty passwords permitted. They then use Satellite's built-in Ansible remediation snippet to fix the violation on the affected hosts and confirm the remediation succeeded. This module demonstrates the full Red Hat Satellite compliance lifecycle: scan, report, remediate, verify.

## Audience and Time

- **Target personas:** Systems administrators, IT security professionals, Satellite administrators
- **Prerequisites for this module:** All previous modules complete; OpenSCAP client installed on rhel1.lab and rhel2.lab (module 08); compliance policy "DISA STIG no empty passwords ssh" created and associated with the RHEL10 host group (module 06)
- **Estimated duration:** 8 minutes

## Learning Objectives

- Trigger an OpenSCAP compliance scan on managed hosts using Red Hat Satellite
- Interpret a Satellite compliance report to identify policy violations
- Remediate a compliance violation using Satellite's Ansible-based remediation snippet

## Detailed Steps

1. In the Satellite Web UI, navigate to **Hosts > All Hosts**.
2. Select both rhel1.lab and rhel2.lab using the checkboxes.
3. Click the accordion next to **Schedule a job** and select **Run OpenSCAP scan**.
4. Confirm the scan is triggered for both rhel1.lab and rhel2.lab — a Remote Execution job is created.
5. Navigate to **Monitor > Jobs** and find the OpenSCAP scan job.
6. Wait for the job to complete on both hosts — observe the real-time task output showing the oscap command being executed.
7. Once both hosts complete (green status), navigate to **Hosts > Compliance > Reports**.
8. Click the **Reported At** field for rhel1.lab to open its compliance report.
9. Review the report summary: note the pass/fail counts and the overall compliance percentage.
10. Filter or scroll to find the failing rule — it should be the SSH "PermitEmptyPasswords" rule.
11. Click on the failing rule to expand the detail: observe the rule description, rationale, and the current system value.
12. In the **Actions** column, click the accordion next to **Hosts failing this rule** and select **Remediation**.
13. On the remediation page, select **Remote job**, then open the **Snippet** dropdown and select **Ansible**.
14. Click **Next**, then **Review remediation**, then **Run**.
15. Click the **Job details** button to monitor the remediation job completion.
16. Review the Reference Materials section in the module for links to openscap.org, Red Hat Satellite documentation, and the Satellite Basics lab.

## Key Takeaways

- Satellite's compliance scanning workflow (policy → scan → report → remediate) is entirely GUI-driven once the initial setup is complete, lowering the barrier for security teams to enforce compliance across large fleets
- The ARF (Asset Reporting Format) report generated by the OpenSCAP client is automatically uploaded to Satellite and translated into the human-readable compliance report — administrators do not need to collect or parse raw XML
- Ansible-based remediation snippets in Satellite are derived from the SCAP Security Guide's own remediation content, ensuring the fix is aligned with the same authoritative source as the scan rule
- The tailoring file restricts the scan to one rule — without it, the scan would check all STIG benchmark rules
- The capstone violation (SSH PermitEmptyPasswords) is intentionally simple — it demonstrates the full workflow without requiring complex multi-step remediation, but the same pattern applies to any rule in the STIG profile

## Infrastructure Notes

- The scan is triggered via Remote Execution and requires the SSH keys set up during host registration (module 07) to be functional
- Scan duration varies; in a lab environment with a targeted tailoring file (single rule), the scan should complete in under 60 seconds per host
- The compliance report appears in Satellite after the foreman_scap_client cron job uploads the ARF report — for on-demand scans triggered via the job scheduler, the upload happens at the end of the scan job automatically
- If the report does not appear within 2 minutes after job completion, check the satellite.lab terminal for upload errors in `/var/log/foreman/production.log`
- The lab concludes with a Reference Materials section containing links to openscap.org, Red Hat Satellite documentation, and the Satellite Basics lab for further learning
